## 한 줄 회고

검색 방식을 바꾸는 것보다 **무엇을 어떻게 재는가**를 먼저 정하는 일이 더 중요했습니다. 가장 공들인 개선(BM25 한국어 토큰화)은 채택하지 못했지만, 안 바꾼 이유를 숫자로 설명할 수 있게 된 것이 이번 작업의 성과였습니다.

## 개인 회고: 진행하며 궁금했던 것

> 아래는 작업하면서 스스로 궁금해 찾아보고 정리한 내용입니다. 각 항목에 **무엇이 이 프로젝트에서 확인된 것이고, 무엇이 외부 자료로 알게 된 것이며, 무엇이 아직 검증하지 못한 것인지**를 구분해 적었습니다.

### RRF 상수는 왜 60인가

- **프로젝트에서 확인된 것**: 구현의 `RRF_CONSTANT = 60`입니다([`hybrid.py#L30`](https://github.com/kant-proj3-team3/shipping_rag/blob/39a8410305e3f8ada258c8f85516bd6f2e820829/packages/retrieval/src/retrieval/hybrid.py#L30)). 코드 주석은 "RRF 순위 점수 계산에 사용하는 상수"라고만 적고, 60을 고른 이유나 다른 값과의 비교는 기록되어 있지 않습니다.
- **외부 자료로 알게 된 것**: RRF 원논문(Cormack, Clarke, Büttcher, SIGIR 2009)은 `1 / (k + 순위)`의 합으로 순위를 결합하고, **k = 60을 사전 파일럿 실험에서 정해 이후 검증에서 바꾸지 않았다**고 밝힙니다. 파일럿 결과(TREC 주제 351 ~ 400, Wumpus 30개 설정 결합)에서 k=60 부근이 최적에 가까웠지만 **값의 선택이 결정적이지는 않았습니다.** k=10 ~ 100에서 MAP 차이가 0.003 미만이었고, k=0과 k=500은 눈에 띄게 낮았습니다. 그래서 60이 널리 쓰이는 기본값이 되었다고 이해했습니다. 정확히는 "모든 데이터셋에서 가장 좋은 값으로 증명된 것"이 아니라 "민감하지 않은 안정적인 기본값"입니다. ([논문](https://dl.acm.org/doi/10.1145/1571941.1572114))
- **검증하지 못한 것**: 이 프로젝트의 데이터(한국어 해운 문서, 56문항)에서 k=60이 최적인지는 비교하지 않았습니다. 논문의 결과가 이 데이터에도 같다고 단정하지 않습니다.

### Hybrid + Rerank는 왜 Hybrid보다 느린가

- 리랭킹은 후보 50개를 cross-encoder에 질문과 함께 한 쌍씩 넣어 다시 채점하는 **추가 연산**입니다. Dense·BM25 검색과 RRF 결합은 순위만 다루지만, 리랭커는 모델을 질문당 50쌍에 대해 실행합니다.
- **프로젝트에서 측정된 것**(보고서 6장): 60문항 전체 평가 시간이 Hybrid 약 4 ~ 10초, Hybrid + Rerank 약 78 ~ 119초였고, 리랭커 단독 측정은 질문당 평균 1.28초(50쌍)였습니다. 후보 수가 50개로 고정이라 k를 바꿔도 리랭킹 시간은 거의 같았습니다. CPU에서는 질문당 8 ~ 17초였습니다.

### BM25 토큰화는 왜 바꾸지 않았나

형태소 분리(Kiwi)와 조사 분리(josa)를 적용해 regex와 비교했습니다. 비교는 k=5·10·20 모두에서 했고, 최종 선택인 k=10의 Hybrid + Rerank Recall은 regex 0.765, josa 0.768, kiwi 0.764로 차이가 없었습니다. BM25 단독 순위는 좋아졌지만 최종 Hit·Recall 변화는 대부분 ±0.02 이내이고 방향이 엇갈려, 의존성 추가 비용에 비해 개선이 분명하지 않다고 보고 **기존 regex를 유지**했습니다(위 1-1절).

### k를 5에서 10, 20으로 넓혀 비교한 이유와 k=10 선택

- 기존에 쓰던 top-k는 5였고, 추가로 k=10과 k=20을 비교했습니다. 같은 인덱스·같은 질문으로 평가했습니다.
- **측정된 것**: Hybrid + Rerank의 page Recall@k는 k=5 0.676, k=10 0.765, k=20 0.808이고, page Hit@k는 k=10과 k=20이 0.982로 같습니다. k=20의 Recall이 가장 높았습니다.
- **보고서의 설명**: 보고서 8장은 "Recall은 k=20까지 오르지만 그만큼 답변 프롬프트의 토큰·비용이 늘어난다"고 설명하며 k=5~10을 권고합니다. 이 설명을 근거로 **최종적으로 k=10을 선택**했습니다.
- **검증하지 못한 것**: k=10과 k=20의 실제 답변 품질·토큰·비용·생성 지연을 직접 비교한 결과는 없습니다. 토큰·비용 증가는 측정이 아니라 보고서가 든 설명입니다. 자세한 구분은 [프로젝트 상세의 "k 선택"](README.md#k-선택-최종-k10-근거의-범위-구분)에 있습니다.

### 가장 아쉬운 점: 문서는 맞고 페이지가 틀린 경우

세 방식 모두 page Recall이 document Recall보다 0.09 ~ 0.14 낮았고, 근거 그룹 178개 중 16 ~ 21개(9 ~ 12%)가 **문서는 맞고 페이지가 틀린 경우**였습니다. 맞는 문서를 찾는 단계보다 정확한 페이지를 고르는 단계가 병목이었다는 뜻이고, 다음 실험의 가장 큰 동기입니다.

### 후보를 50개씩 가져온 이유와 남은 질문

- **프로젝트에서 확인된 것**: Dense와 BM25에서 각각 최대 50개를 가져와 RRF로 결합하고, 그 상위 50개를 리랭킹합니다(`CANDIDATE_POOL = 50`, [`hybrid.py#L31`](https://github.com/kant-proj3-team3/shipping_rag/blob/39a8410305e3f8ada258c8f85516bd6f2e820829/packages/retrieval/src/retrieval/hybrid.py#L31)). 코드 주석은 "Dense와 BM25에서 각각 가져올 최대 후보 수"라고만 적습니다.
- **내 설명(작성자 해석)**: 최종 top-k(5·10·20)보다 넓은 후보 집합을 확보해 두기 위해 최대 50개씩 가져왔습니다. 이 이유는 코드 주석이나 보고서에 따로 기록된 것은 아닙니다.
- **검증하지 못한 것**: 후보 수는 50으로 **고정**했고, 50이 최적인지는 검증하지 않았습니다. 더 적게 하면 리랭킹 비용이 줄고 더 많이 하면 Recall이 오를 수 있지만, 어느 쪽이 나은지 이 프로젝트에서는 측정하지 않았습니다. 최적의 값을 찾기 위한 **후보 수 비교 실험**을 해 보고 싶습니다(아래 "다음 실험" 참고).

## 1. 실패한 시도

### 1-1. BM25 한국어 토큰화 (채택하지 않음)

**왜 시작했나.** `IS-ADD-10`이 k=20에서도 세 방식 모두 page Hit 0이었습니다. 추적해 보니 근거 청크는 색인에 온전히 있었고(청킹 문제 아님), Dense 순위는 31위, BM25 순위는 480위였습니다. 질문의 `정정합니다`, `vgm을`과 근거의 `정정은`, `vgm의`가 다른 단어로 취급된 것이 원인이었습니다. BM25 순위가 낮아 RRF 결합 후 50위 밖으로 밀리면서 리랭커가 후보를 보지 못했습니다.

**어떻게 했나.** 환경변수(`BM25_TOKENIZER`)로 regex(기존) / josa(조사 규칙) / kiwi(형태소 분석)를 고르게 하고, 같은 인덱스·같은 골든·같은 GPU에서 비교했습니다. 바꾸지 않은 설정을 한 번 더 돌려 기준선과 문항별로 완전히 같은지 먼저 확인했고, 평균에 가려지는 변화를 보려고 문항별 비교표와 DEV / ADD 분리를 썼습니다.

**1차 구현이 틀렸던 부분.** 실제 청크에 돌려 보니 전문용어를 잘못 나눴습니다.

| 방식 | 원문 | 1차 결과 | 문제 |
|---|---|---|---|
| josa | `정확도` | `정확` | 명사 끝 글자 `도`를 조사로 착각 |
| kiwi | `선적서류` | `선적`, `서류` | 복합명사 분해 |
| kiwi | `GR26-P0670` | `gr`, `26`, `p`, `0670` | 식별자 분해 |
| kiwi | 일련번호·이메일 | 사라짐 | 해당 품사를 버림 |

해운 문서는 붙여 쓴 전문용어와 식별자가 검색의 핵심 단서라, "조사는 떼되 단어 안쪽은 건드리지 않는다"로 원칙을 바꿨습니다. kiwi는 형태소를 다시 조립하는 방식이 표 형식 청크에서 품사를 자주 틀려서(`화물총중량`, `기록일`, `1대`), **띄어쓰기 단어를 기준으로 두고 Kiwi는 끝의 조사 위치만 판단**하는 방식으로 바꿨습니다.

**결과와 결정.**

비교는 **k=5·10·20 모두**에서 같은 조건(page 기준, 채점 56문항)으로 했습니다. 최종 선택 k=10의 결과를 따로 짚으면 다음과 같습니다.

| 지표 | regex | josa | kiwi |
|---|---|---|---|
| BM25 50위 안 근거 그룹 (178개 중) | 133 | 136 | **144** |
| BM25 최고 순위 중앙값 | 7 | 8 | **5** |
| **Hybrid + Rerank Recall@10** (최종 설정) | 0.765 | 0.768 | 0.764 |
| Hybrid + Rerank Hit@10 | 0.982 | 0.982 | 0.982 |
| Hybrid Recall@10 | 0.700 | 0.701 | 0.694 |

| Recall@k (Hybrid + Rerank) | regex | josa | kiwi |
|---|---|---|---|
| k=5 | 0.676 | 0.685 | 0.681 |
| k=10 | 0.765 | 0.768 | 0.764 |
| k=20 | 0.808 | 0.817 | 0.820 |

- BM25 단독 순위는 분명히 좋아졌지만 **최종 Hit·Recall 변화는 대부분 ±0.02 이내**이고 DEV는 떨어지고 ADD는 올라 방향이 엇갈렸습니다. **최종 선택인 k=10의 Hybrid + Rerank에서는 차이가 0.003 이내**(josa +0.003, kiwi -0.001)로 사실상 없었습니다.
- 문항별로는 움직였습니다. Hybrid + Rerank k=10에서는 kiwi 3문항 개선·4문항 하락, josa 2문항 개선·2문항 하락이었고, Hybrid k=20의 kiwi는 7문항 개선·11문항 하락이었습니다. 평균이 비슷한 것은 상쇄 효과였습니다.
- `IS-DEV-28`은 근거 그룹의 BM25 순위가 10→56위, 3→159위로 떨어졌습니다. 조사를 떼면서 흔한 단어가 더 많은 청크와 일치하게 된 것으로 추정하지만, **검증하지는 못했습니다.**
- 정작 목표였던 `IS-ADD-10`도 BM25 순위가 205→113(josa)·140(kiwi)위로 올랐을 뿐 50위 안에는 들지 못했습니다.
- `kiwipiepy` 의존성과 팀 공용 `uv.lock` 변경, 유지할 규칙이 늘어나는 비용이 개선 폭보다 크다고 판단해 **regex를 유지**했습니다. 실험 코드는 커밋하지 않고 `improvement_log.md`에 핵심만 보존했습니다.

### 1-2. 리랭커 입력 한도 (바꿀 이유가 없었음)

리랭커 입력은 `질문 + 청크`인데 청크 한도와 리랭커 한도가 모두 512라 질문이 들어갈 자리가 없고, 넘치면 오류 없이 뒤쪽이 잘립니다. 512 / 1024 / 2048을 비교한 결과 점수 변화는 0 / 56이었습니다. 리랭커에 실제로 들어간 2,800쌍 중 가장 긴 것이 504토큰이라 잘린 쌍이 없었습니다. **512를 유지**했지만 여유가 8토큰뿐이고, "잘리지 않는다"는 코드가 보장하는 성질이 아니라 이번 질문에서 잰 결과일 뿐입니다.

### 1-3. Hybrid가 Naive를 이기지 못한 구간

page k=5에서 Hybrid(Recall 0.596)는 Naive(0.619)보다 낮았습니다. Hybrid가 근거를 하나도 못 찾은 7문항 중 6문항은 document 기준으로는 찾았습니다. BM25가 맞는 문서는 가져오지만 상위 5개 안에 정확한 페이지를 넣지는 못했습니다. 리랭킹을 붙이기 전에는 BM25 결합이 만능이 아니었습니다.

## 2. 아쉬운 점

1. **`IS-ADD-10`을 끝내 풀지 못했습니다.** 문서(`IS04`)는 모든 방식에서 상위에 나오지만 정답 페이지(p1)를 가져오지 못했습니다. 질문은 날짜·장비가 있는 구체적 사례이고 근거는 일반 규칙이라 표현 차이가 컸고, 리랭커도 후보에 들어오지 않은 청크는 점수를 매길 수 없었습니다. 근거 청크를 리랭커에 직접 넣으면 0.49, 상위 청크는 0.96 ~ 0.99였습니다. 이 문항은 정답 근거 후보가 1개뿐이라 같은 답을 뒷받침하는 다른 페이지를 찾아도 0점입니다. 답변 평가에서는 맞을 수 있지만 **확인하지 못했습니다.**
2. **표본이 작았습니다.** 56문항이라 ±0.02 차이는 우연과 구분하기 어려웠습니다. 그래서 개선이 아니라 "차이를 확인하지 못했다"고 쓸 수밖에 없는 실험이 많았습니다.
3. **추가 실험을 page 기준으로만 했습니다.** CPU·GPU 비교와 BM25 토큰화는 document 기준으로 같은 결론인지 확인하지 않았습니다.
4. **리랭킹 지연을 해결하지 못했습니다.** GPU에서 질문당 약 1.3초, CPU에서는 8 ~ 17초였고, 동시에 3개를 요청하면 최대 36.3초까지 늘었습니다. 원인(CPU 리랭킹, 리랭커 잠금 대기, 첫 요청의 모델 로딩, Docker에서 모델 재다운로드)은 정리했지만 **개선은 적용하지 못했습니다.**
5. **평가 데이터를 공개하지 못해** 포트폴리오만으로는 평가를 재현할 수 없습니다.
6. **k=10 선택을 실측으로 검증하지 못했습니다.** 검색 지표(page Hit 포화, Recall 증가폭)와 보고서의 토큰·비용 권고에 근거해 k=10으로 정했지만, k=10과 k=20의 답변 품질·토큰·비용·생성 지연을 직접 비교하지는 않았습니다. 백엔드 문맥 예산(기본 12,000토큰) 때문에 k=20의 청크가 모두 전달되는지도 확인하지 못했습니다. 자세한 구분은 [프로젝트 상세의 "k 선택"](README.md#k-선택-최종-k10-근거의-범위-구분)에 있습니다.
7. 검색 점수와 답변 품질의 관계를 직접 확인하지 못했습니다. 팀의 답변 평가에서도 실패의 대부분이 검색 단계에서 근거를 못 가져온 경우였다는 분석이 있었지만, 검색 지표와 답변 점수를 문항별로 연결한 분석은 하지 않았습니다.

## 3. 잘한 점 (다음에도 유지)

- **같은 조건 비교.** 같은 임베딩·인덱스·k·질문, 두 fingerprint 기록, 대조군 실행으로 "바꾼 것의 효과"만 보이게 했습니다.
- **평가 단위를 둘로 나눔.** page만 봤다면 "Hybrid가 Naive보다 나쁘다"로 끝났을 텐데, document를 함께 보니 페이지 선정 단계의 문제라는 것이 보였습니다.
- **영향 범위를 먼저 분류.** 토큰화를 바꾸기 전에 회복을 기대하는 문항 15개, 둘 다 못 찾는 문항 20개, BM25 덕을 보는 회귀 위험 문항 23개로 나눠, 식별자를 쪼개지 않는다는 조건을 처음부터 세웠습니다.
- **안 바꾼 결정도 기록.** 효과가 없다는 것을 확인한 실험의 수치와 이유를 남겨 팀원이 반복하지 않게 했습니다.
