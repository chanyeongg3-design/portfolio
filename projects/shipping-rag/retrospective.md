## 한 줄 회고

"검색 방식을 바꾸는 것보다, **무엇을 어떻게 재는가**를 먼저 정하는 일이 더 중요했다."

## Keep: 계속할 것

### 1. 같은 조건에서만 비교하기
세 검색 방식을 같은 임베딩, 같은 저장소, 같은 k, 같은 질문으로 돌렸고, `index_fingerprint`와 `golden_fingerprint`를 보고서에 남겼습니다. 그래서 "어떤 방식이 낫다"는 결론이 인덱스나 데이터가 바뀐 탓이 아니라는 것을 확인할 수 있었습니다.

### 2. 평가 단위를 둘로 나누기
처음에는 page 기준 점수만 봤다면 "Hybrid가 Naive보다 나쁘다"로 끝났을 것입니다. document 기준을 함께 보니 Hybrid는 맞는 문서는 더 잘 찾고 **정확한 페이지에서 밀리는** 것이었습니다. 지표를 하나 더 두면 실패가 어느 단계에서 났는지 보입니다.

### 3. 바꾸지 않기로 한 실험도 기록하기
리랭커 입력 한도(512 / 1024 / 2048)와 BM25 토큰화(regex / josa / kiwi)는 시험해 보고도 **현재 설정을 유지**했습니다. 점수 변화가 0이거나 ±0.02 안에서 방향이 엇갈렸기 때문입니다. 안 바꾼 이유까지 문서에 남겨 두니 팀원이 같은 실험을 반복하지 않아도 되었습니다.

### 4. 모듈 경계와 계약
모듈이 `common` 계약만 import하게 하고 `import_lint.py`로 검사한 덕분에, 4명이 동시에 작업해도 서로의 코드에 막히지 않았습니다. 목업 구현이 기본값이라 키·DB 없이도 테스트와 CI가 돌았습니다.

## Problem: 어려웠던 점

### 1. 맞는 문서를 찾고도 페이지를 놓친다
세 방식 모두 page Recall이 document Recall보다 0.09 ~ 0.14 낮았습니다. 대표 사례가 `IS-ADD-10`입니다.
- 질문은 날짜·장비가 들어간 구체적 사례, 근거는 일반 규칙이라 표현이 달랐습니다.
- BM25는 `정정합니다`와 `정정은`을 다른 단어로 취급했습니다.
- 리랭커 점수를 확인해 보니 근거 청크를 직접 넣었을 때 0.49, 상위 청크는 0.96 ~ 0.99였습니다. 합친 순위 50위 밖이라 리랭커가 아예 보지 못한 것이 직접 원인이었습니다.

### 2. 한국어 BM25
형태소 분석(Kiwi)으로 BM25 단독 성능은 올랐습니다(BM25 50위 안 근거 그룹 133개 → 144개). 그런데 최종 Hybrid + Rerank 성능은 거의 그대로였습니다. **부분 지표가 좋아져도 전체 파이프라인이 좋아진다는 보장은 없다**는 것을 확인했습니다.

### 3. 리랭킹 비용
리랭킹이 검색 시간의 대부분을 차지했습니다. GPU에서 질문당 약 1.3초, CPU에서는 8 ~ 17초였습니다. 후보 수가 50개로 고정이라 k를 바꿔도 시간은 비슷했습니다. 정확도와 지연 시간의 균형은 이번에 다 풀지 못했습니다.

### 4. 평가 데이터의 한계
채점 문항이 56개뿐이라 0.02 안팎의 차이는 우연과 구분하기 어려웠습니다. 정답 근거가 하나뿐인 문항은 같은 뜻의 다른 페이지를 찾아도 0점이었습니다. 검색 점수가 낮은 것과 답변이 틀린 것은 다를 수 있습니다.

### 5. 측정 노이즈와 운영 문제 (팀 전체)
같은 조건으로 2회 돌려도 문항 3건 안팎이 뒤집혔습니다. 평가 실행은 채점 모델 API 대기 때문에 느렸고, 병렬로 돌리면 한 회차가 약 65분 멈추기도 했습니다. Windows Git Bash에서는 경로 변환과 한글 JSON 인코딩 문제도 있었습니다.

## Try: 다음에 해볼 것

| 우선순위 | 시도 | 이유 |
|---|---|---|
| 1 | RRF 결합 조정(가중치, 상수 60) | BM25 순위 개선이 최종 결과에 반영되지 않는 원인이 결합 단계에 있는지 확인 |
| 2 | 페이지 선정 개선, 질문을 하위 질문으로 나눠 검색 | 문서는 맞고 페이지가 틀린 9 ~ 12%를 줄이기 위해 |

| 4 | 평가 문항 늘리기, 정답 근거 후보 보강 | 56문항으로는 작은 차이를 판단하기 어렵고 정답 근거가 1개뿐인 문항이 있음 |
| 5 | 추가 실험을 document 기준으로도 확인 | CPU·GPU 비교와 BM25 토큰화는 page 기준만 확인함 |

## 배운 점 요약

1. **측정이 먼저다.** 평가 단위, 조건, 노이즈 크기를 먼저 정해야 개선인지 우연인지 말할 수 있습니다.
2. **지표는 둘 이상 본다.** page와 document처럼 관점이 다른 지표를 함께 봐야 실패의 위치가 보입니다.
3. **안 바꾼 결정도 결과다.** 효과가 없다는 것을 확인하는 것도 실험의 성과이고, 기록해 두면 다음 사람의 시간을 줄입니다.
4. **실패의 대부분은 검색에서 났다.** 프롬프트를 아무리 고쳐도 근거가 검색되지 않으면 답이 나오지 않았습니다. RAG는 검색 품질의 상한이 곧 답변 품질의 상한입니다.
5. **계약과 목업이 협업 속도를 만든다.** 모듈 경계를 코드로 검사하고 키 없이 돌아가는 목업을 두면 병렬 작업이 쉬워집니다.
